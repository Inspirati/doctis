# GIT-DESIGN.md — Doctis Git Backend: Design Rationale and Architecture

This document records the deliberations and decisions that shaped how Doctis
uses git as its document storage backend. It is intended as the authoritative
reference for understanding _why_ the system is designed the way it is, not
just _what_ it does.

---

## Governing principle

**Doctis is a lightweight document index and lifecycle tracking system that
uses git as its storage backend. It is not a git forge, not a GitHub
replacement, and not a document version navigation tool.**

All design decisions should be tested against this principle. The moment a
proposed feature starts managing branches, displaying diffs, showing commit
graphs, or providing contributor views — it belongs in git tooling, not in
Doctis.

---

## The separation of concerns

### Git's role

Git is the **collaborative storage and versioning infrastructure**. Multiple
developers can clone, branch, commit, push, and merge against the bare
repositories using standard git tooling, independently of Doctis. None of
that activity needs to be visible to, or driven by, Doctis.

### Doctis's role

Doctis is the **lifecycle and index layer**. It owns:

- Document metadata (title, reference, revision, classification, etc.)
- Workflow state (status, assignment, review, approval)
- Access control and license requirements
- The record of _which specific git version_ is associated with each
  significant lifecycle event

All meaningful state transitions are initiated from the Doctis interface.
The direction of control is always **Doctis → git**, never git → Doctis.

## Repository layout

Each Doctis project maps to exactly one bare git repository:

```
/var/git/doctis/<project-slug>.git      bare repo (authoritative store)
/var/www/doctis/worktrees/<project-slug> Doctis's own working tree
```

The slug is derived deterministically from the project name
(`project_slug()` in `GitFileStorageBackend`). The mapping is one-to-one
and permanent:

```
Doctis project → project_id → slug → /var/git/doctis/<slug>.git
```

The bare repo is created automatically on first use (`ensure_project_repo()`).

### File paths within the repo

Every document file is stored at:

```
<dwg_id>/<filename>        e.g.  4/spec-rev-b.md
```

The `dwg_id` is structurally embedded in every path, providing the permanent
link back to the Doctis database record.

---

## What Doctis stores — and why the folder is redundant

The current `dwg_primary_file` table stores:

| Column | Purpose |
|--------|---------|
| `diskfile` | Commit SHA — the specific version Doctis last recorded |
| `folder` | Absolute path to the bare repo |
| `filename` | Original filename |
| `filesize`, `file_type`, etc. | File metadata |

The `folder` column is **redundant**. Since every Doctis operation occurs
within a known project context, the bare repo path is always mechanically
derivable:

```
dwg_id  →  project_id (via dwg table)
        →  slug (via project_slug())
        →  /var/git/doctis/<slug>.git
```

The SHA is the **only** variable, version-specific piece of information that
must be explicitly stored. Everything else is either structural (derivable
from the project context) or metadata about the file itself.

The `folder` column is retained for now as harmless defensive scaffolding
from the initial implementation, but carries no information not already
present in the data model.

## Document entry points — ways a git object enters Doctis

A Doctis document record (`dwg` table row) can be created and associated with
a git object via several independent paths:

| Entry path | Git object created? | SHA source |
|------------|--------------------|-----------:|
| Placeholder record (no file) | No | — |
| Record created with immediate file upload | Yes (new commit) | Generated by upload |
| File uploaded to existing placeholder record | Yes (new commit) | Generated by upload |
| Record created/modified with reference to existing git object | No | Supplied by caller |
| SHA updated at a lifecycle transition | No | Supplied or read from HEAD |

The first three paths are fully implemented. The fourth and fifth require
a "register SHA" mechanism — a path that sets `diskfile` (and validates the
SHA exists in the project repo via `git cat-file -t`) without performing a
file upload. This is the same operation; the upload path is a convenience
that generates the SHA automatically.

## The lifecycle SHA update — the central design question

As a document evolves through development, developers push new commits to the
bare repo. Doctis holds only the SHA it last recorded — which drifts behind
the live repository. The question is: how and when does the recorded SHA
advance?

### Resolution

The SHA does **not** need to be kept continuously current. It only needs to be
current **at the moment of a lifecycle transition** in Doctis. Between
transitions, Doctis deliberately has no visibility into what developers are
doing in git — that is the correct scope boundary.

At the point a lifecycle transition is requested (submit for review, approve,
incorporate), the relevant party provides the SHA. Two mechanisms:

1. **Direct entry** — the developer (or a Doctis user with write access)
   enters the SHA manually. Suitable for technical users and CI integration.

2. **"Use current HEAD" action** — Doctis reads `HEAD` from the project's
   bare repo (`git rev-parse HEAD`) on the user's behalf. Doctis-driven,
   requires no git knowledge from the user, no hooks.

Both result in Doctis recording an updated SHA. Neither requires automation
on the git side.

### No git hooks driving Doctis

There are no `post-receive` hooks or webhooks that push state from git into
Doctis. The control flow is strictly one-directional. This keeps the systems
decoupled and avoids Doctis becoming a git event consumer.

## What Doctis does at each lifecycle event

| Doctis action | Git operation |
|---------------|--------------|
| File uploaded / SHA registered | Record SHA in `dwg_primary_file.diskfile` |
| Submit for review | Record SHA in history entry ("version submitted for review") |
| Approve | Record SHA in history entry ("approved version"); optionally tag the commit |
| Incorporate / release | Invoke pandoc pipeline at the approved SHA; record in history |
| Reject → back to development | No git operation |

### SHA in the history log

Rather than a dedicated SHA column on the `dwg` record, the SHA travels with
significant status transitions in the Doctis history log. This provides the
ISO 9001 audit record: at the point the document moved to status X, the git
commit was Y. The history log is the bridge between Doctis's workflow and
git's commit history.

### Git tagging

Placing a tag in the bare repo at approval (`git tag dwg<id>/approved-<rev>`)
is a useful navigational aid when browsing the repo directly. It is **not**
essential to Doctis functionality — the SHA record is sufficient. Tagging is
a nicety to be added when the workflow is in active use.

---

## What Doctis does NOT do

- Display commit history or diffs
- Manage branches
- Show contributor graphs
- Provide pull request or code review workflows
- Act as a general git repository browser

These belong in git tooling (a git client, a forge such as Gitea or GitHub).
Doctis's only legitimate git-facing operations are:

- **Read** — retrieve file content at a stored SHA
- **Write** — store a new file version (via upload, generating a new commit)
- **Register** — record an existing SHA against a document record
- **Tag** — optionally mark an approved commit (nicety, not required)
- **Trigger** — invoke the pandoc pipeline at the incorporation step

---

## Pandoc pipeline

The pandoc pipeline is a separate concern. It is:

- **Triggered** by the Doctis incorporation/release step
- **Sourced** from the git repo at the recorded approved SHA
- **Independent** of the Doctis/git integration design described here

Its only relationship to git is as a data source. The pipeline specification
(input format, output format, destination) is defined separately.

---

## Developer access to repositories

Developers access the bare repos directly using standard git:

```bash
git clone hcr@vaio:/var/git/doctis/example.git
```

This is entirely independent of Doctis. Developers push freely as part of
normal iterative development. Doctis is unaware of this activity until a
lifecycle transition explicitly records a SHA.

The bare repos are at `/var/git/doctis/` on vaio, owned by `www-data:www-data`,
mode `2770`. Developers in the `www-data` group can read and push directly.
